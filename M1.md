# ChalkTalk

## M1 — Proposal and Requirements

ChalkTalk is a course discussion platform for students, TAs, and instructors. It is designed to make large course forums easier to search, organize, and maintain as the number of posts grows throughout a semester.

---

## Problem

Platforms such as Piazza and Ed Discussion can become difficult to navigate in large courses. Over a semester, a class may accumulate hundreds or thousands of posts about assignments, deadlines, lecture material, course policies, exams, and debugging questions.

Students often ask questions that have already been answered because finding an old post requires knowing the right keywords or manually searching previous discussions. This leads to:

- duplicate questions,
- instructors and TAs repeatedly answering the same questions,
- useful answers becoming buried,
- students struggling to identify authoritative answers,
- course staff struggling to find unresolved questions.

**ChalkTalk** is designed to make old course discussions easier to reuse.

When a student writes a question, ChalkTalk shows similar existing questions before the new post is submitted. Search also supports semantic similarity, so students do not need to use the exact wording of an existing post.

For example:

```text
Student:
"When do we have to submit Homework 3?"

Existing post:
"HW3 submission deadline clarification"
```

ChalkTalk should recognize that these are likely about the same topic.

---

## Users

### Students

Students can:

- search previous discussions,
- ask and answer questions,
- contribute to shared student answers,
- participate in follow-up discussions,
- view course resources,
- vote in polls,
- follow discussions,
- optionally post anonymously.

### Teaching Assistants

TAs can:

- answer questions,
- collaborate on staff answers,
- endorse correct answers,
- moderate discussions,
- mark duplicate posts,
- manage tags and resources,
- find unanswered questions.

### Instructors

Instructors can:

- create and manage courses,
- manage course roles,
- upload course materials,
- moderate discussions,
- configure course settings,
- archive courses,
- view basic course statistics.

---

## Why This Is a Semester Project

ChalkTalk is not a single feature or an AI wrapper. It combines several systems that share persistent data and must work correctly together:

- user accounts and authentication,
- multiple courses,
- student, TA, and instructor permissions,
- discussion posts and nested replies,
- collaborative answers,
- concurrent editing,
- semantic and full-text search,
- duplicate detection,
- anonymity,
- file uploads,
- course resources,
- moderation,
- notifications,
- statistics.

These features also interact.

For example, search must never return posts from a course the user cannot access. Anonymous users must remain anonymous in search results and notifications. Two TAs editing the same shared answer should not accidentally overwrite each other's work.

This makes ChalkTalk a multi-user system with shared state, permissions, concurrency, search, security, and several complete workflows.

## Core Workflows

### Asking a Question

```text
Student starts writing a question
            |
            v
ChalkTalk shows similar existing posts
            |
      +-----+-----+
      |           |
      v           v
Existing       No useful
answer found   answer found
      |           |
      v           v
Open post      Submit question
```

### Resolving a Question

```text
Student posts question
        |
        v
TA writes or edits staff answer
        |
        v
Another TA/instructor may improve it
        |
        v
Staff endorses the final answer
        |
        v
Students see an authoritative response
```

### Searching Course History

```text
Student enters a search
        |
        v
Full-text + semantic search
        |
        v
Permissions and anonymity rules applied
        |
        v
Relevant discussions returned
```

## User Stories

### Students

**As a student, I want to search using normal language so that I can find an answer even if I do not know the exact wording of the original post.**

**As a student, I want to see similar questions while writing a post so that I can avoid asking something that was already answered.**

**As a student, I want to write questions using Markdown, LaTeX, images, and documents so that I can clearly explain technical questions.**

**As a student, I want to post anonymously so that I can ask a question without exposing my identity to classmates.**

**As a student, I want to contribute to a shared student answer so that several students can improve the same explanation.**

**As a student, I want to ask follow-up questions so that I can continue a discussion when an answer is unclear.**

**As a student, I want to follow a discussion so that I know when it receives new activity.**

### Teaching Assistants

**As a TA, I want to contribute to a shared staff answer so that course staff can maintain one authoritative response.**

**As a TA, I want to endorse a correct answer so that students can quickly identify trusted information.**

**As a TA, I want to mark a question as a duplicate so that repeated discussions point students toward an existing answer.**

**As a TA, I want to filter for unanswered questions so that I can quickly find students who still need help.**

### Instructors

**As an instructor, I want to create and manage a course so that students and TAs have an isolated discussion space.**

**As an instructor, I want to assign course roles so that TAs have the correct permissions.**

**As an instructor, I want to upload course resources so that important documents are available in one place.**

**As an instructor, I want to moderate and archive a course so that the forum stays organized during and after the semester.**

## Functional Requirements

### Accounts

Users can:

- register using a `.edu` email address,
- verify their email,
- log in and log out,
- reset a forgotten password,
- change their password,
- modify their account,
- delete their account.

Passwords must be securely hashed and never stored in plaintext.

Password-reset and email-verification links must expire.

---

### Courses

Users can create independent course forums.

The creator of a course becomes its instructor.

Students can join using a course-specific join code.

Each course supports three roles:

- Student
- Teaching Assistant
- Instructor

A user's role can be different between courses.

Instructors can promote or remove TAs.

Courses can be archived or deleted.

An archived course:

- remains readable,
- remains searchable,
- does not allow new posts,
- does not allow new replies,
- does not allow new members.

---

### Posts

ChalkTalk supports three post types:

- Questions
- Notes
- Polls

Posts contain:

- an author,
- a creation timestamp,
- a last-edited timestamp,
- content,
- tags,
- an anonymity setting.

Posts support:

- Markdown,
- LaTeX,
- images,
- document uploads.

---

### Questions and Answers

Any course member can ask a question.

While the user writes the question, ChalkTalk shows similar existing posts from the same course.

Each question can have:

- one shared student answer,
- one shared staff answer.

Students can edit the student answer.

TAs and instructors can edit the staff answer.

Contributors to shared answers are recorded.

TAs and instructors can endorse an answer. An endorsed answer is visibly marked and becomes read-only until the endorsement is removed.

#### Concurrent Editing

Because several people may edit the same answer, ChalkTalk must prevent silent overwrites.

For example:

```text
User A and User B both open version 5.

User A saves first.
The answer becomes version 6.

User B tries to save changes based on version 5.

ChalkTalk detects the outdated edit instead of
silently overwriting User A's changes.
```

---

### Threads

Questions and answers can have follow-up discussions.

Follow-ups can themselves receive replies, creating a nested thread.

Users can:

- reply,
- edit their own replies,
- collapse nested branches.

TAs and instructors can lock a discussion. Locked discussions remain readable but cannot receive new replies.

---

### Notes

Notes are informational posts.

They do not contain shared answer slots.

---

### Polls

TAs and instructors can create polls.

Course members can vote.

Polls contain a list of choices and prevent invalid duplicate votes.

Vote counts must remain correct even when several users vote at the same time.

---

### Search

ChalkTalk supports both full-text and semantic search.

Users can filter results by:

- tag,
- author,
- date,
- post type,
- answered/unanswered status,
- endorsed status.

Search must only return content the current user is allowed to access.

Anonymous authors must remain anonymous in search results.

---

### Similar Question Detection

While a student is writing a question, ChalkTalk searches the existing course discussion for similar posts.

Suggested posts should show:

- title,
- tags,
- answer status,
- whether an endorsed answer exists.

The student can open a suggested discussion without immediately losing their draft.

The system will not prevent a student from submitting a question if they determine that the suggested posts do not answer it.

---

### Tags

Course staff can create course-specific tags such as:

```text
Homework 1
Homework 2
Midterm
Lecture
Logistics
Conceptual
```

Posts can have multiple tags.

Users can filter discussions and search results using tags.

---

### Course Resources

TAs and instructors can upload or link resources such as:

- syllabi,
- lecture notes,
- assignments,
- course policies,
- reference material.

Resources contain:

- title,
- description,
- type,
- uploader,
- upload date.

Searching inside uploaded resources is a stretch goal.

---

### Notifications

ChalkTalk provides basic in-app notifications.

Users may receive notifications when:

- their question receives an answer,
- someone replies to their follow-up,
- their answer is endorsed,
- a followed discussion receives activity.

---

### Statistics

Course staff can view basic statistics such as:

- total questions,
- answered questions,
- unanswered questions,
- posts over time,
- common tags,
- average time to first response.

More detailed analytics are a stretch goal.

---

## Anonymity

Users can post supported content anonymously.

When content is anonymous:

- classmates see `Anonymous`,
- search results show `Anonymous`,
- notifications preserve anonymity,
- API responses must not leak the hidden author's identity.

The backend may still store the author's identity for moderation and abuse prevention.

Anonymity must be enforced by the backend, not simply by hiding a name in the frontend.

Any semantic-search or AI system must follow the same visibility and anonymity rules.

---

## Nonfunctional Requirements

### Security

The system must protect against:

- unauthorized course access,
- privilege escalation,
- account hijacking,
- unauthorized role changes,
- malicious file uploads,
- cross-site scripting,
- unauthorized resource modification,
- accidental exposure of anonymous identities.

Permissions must always be enforced by the backend.

Hiding a button in the frontend is not considered authorization.

---

### Persistence

Successfully submitted information must remain stored after:

- page refresh,
- logout,
- later login,
- normal server restart.

This includes:

- accounts,
- courses,
- memberships,
- posts,
- answers,
- replies,
- resources,
- poll votes.

---

### Performance

Discussion pages should not load an entire semester of posts at once.

Pagination or lazy loading will be used where appropriate.

Search should return results quickly enough for normal interactive use.

A new post should become visible immediately after it is saved. The user should not need to wait for semantic indexing to finish.

---

### Concurrency

Shared operations must remain consistent when multiple users act at once.

In particular:

- collaborative answer edits must not silently overwrite newer edits,
- poll votes must remain consistent,
- role changes must remain consistent,
- answer endorsements must remain consistent.

---

### Reliability

Failed operations must not appear successful.

If saving a post, answer, vote, or other change fails, the user should receive clear feedback.

---

### Usability

Common actions should require only a few steps.

In particular:

- students should be able to ask a question directly from the course page,
- similar questions should appear while the student is writing,
- endorsed answers should be easy to identify,
- opening a suggested duplicate should not unnecessarily destroy the user's draft.

The interface should work on common desktop, laptop, tablet, and mobile browser sizes.

## Definition of a Successful Version 1

A successful version of ChalkTalk should support the following complete workflow:

1. A user creates and verifies an account.
2. An instructor creates a course.
3. Students join the course.
4. The instructor assigns another member as a TA.
5. A student begins writing a question.
6. ChalkTalk shows similar existing questions.
7. The student either finds an existing answer or submits the new question.
8. A TA creates or edits the shared staff answer.
9. Another staff member can edit the answer without silently overwriting previous work.
10. A TA endorses the answer.
11. Another student searches for the same topic using different wording.
12. ChalkTalk returns the existing discussion.
13. Course permissions and anonymity remain correctly enforced.
14. The instructor archives the course.
15. The archived course remains readable and searchable while rejecting new activity.

This demonstrates the main purpose of ChalkTalk while exercising accounts, shared data, permissions, search, collaboration, moderation, and course management.
