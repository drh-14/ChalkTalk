# Daily course email digest

Daily email delivery is automatic for active members of active courses who have [digest emails enabled for that course](courses.md#courseEmailPreferences). This per-course choice defaults to on; there is no account-wide digest preference. Starting with the UTC activity date on which the database migration is deployed, the worker begins dispatching a separate HTML email with a plain-text alternative per eligible course at or after 00:00 UTC for qualifying activity on the previous UTC calendar date. For example, deployment on October 14 makes the first eligible email due at midnight October 15 for October 14 activity. Earlier dates are not backfilled. If the worker process is unavailable, it catches up eligible dates missed after deployment.

Qualifying activity is creation of a post (question or note), shared answer, or root/reply followup by someone other than the recipient. Questions and notes are combined into one **posts** count, with a link for each visible item. The recipient must still be an active member, and the course must still be active. Own activity, edits, votes, endorsements, deleted content, confirmed duplicate questions, followup tombstones, and hidden parent questions are excluded. Empty course days send no email. The message retains full activity counts and displays up to 50 spaced entries with linked post titles and 600-character formatted body previews, using each answer/followup's own text. An entry includes a Read more link only when its body preview is truncated. Remaining activity links back to the course. Markdown and supported HTML are parsed and sanitized; equations are rendered locally as bounded inline PNGs. Up to five attached-image candidates are considered for bounded private inbox copies; oversized or unavailable readable images use authenticated download links. Private posts and their activity are omitted for every recipient, and anonymous contributors' identities are never included.

PostgreSQL stores one durable intent per `(recipient, course, UTC activity date)`. Before the first send, the worker freezes the exact message, including inline image bytes and CIDs, in the outbox. Every attempt rechecks the recipient address, membership, digest preference, course status, and each item's access, lifecycle, and substantive body; if any item becomes invalid, the whole digest is cancelled. Retries reuse the frozen message and a stable Resend idempotency key. The snapshot is cleared on success or cancellation. Resend acceptance is not inbox delivery, and its 24-hour idempotency window does not guarantee exactly-once delivery after a prolonged retry delay. Local development continues to use Mailpit SMTP.
