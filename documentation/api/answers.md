# Answers, followups, and upvotes

This document describes the **implemented text-only API**. Every route requires a valid `__Host-chalktalk_session` cookie and current course membership. Unsafe requests also require an allowed `Origin` and `X-CSRF-Token`. Requests with a body require `Content-Type: application/json`; multipart requests, attachments, and object-store integration are unavailable. Answer text persists in a Yjs document, but this phase uses version-checked REST saves; collaboration tickets, Hocuspocus, and WebSocket editing are unavailable.

All success bodies use `{ "data": ... }` except paginated followup lists, which also include `meta`. Errors use `{ "error": { "code", "message", "requestId" } }`. Invalid JSON fields or a `bodyMarkdown` value outside 1–100,000 non-whitespace characters return `422 validation_failed`. Hidden, deleted, merged, absent, other-course, and nonmember resources return `404 not_found`. Inactive courses reject writes with `409 course_archived` while members may still read their content. Responses to individual versioned resources include `ETag: "vN"`. Conditional writes require the current `If-Match` (`428 precondition_required` if missing, `412 version_conflict` if stale). A note cannot have answers or followups (`409 not_a_question` on creation; `422 not_a_question` on listing).

## Answer cards

A question can have any number of independent answer cards. There are no student or instructor slots or `kind` in the public response. `GET /api/v1/posts/{postId}/answers` returns `{ "data": Answer[] }` in creation order. `GET /api/v1/answers/{answerId}` returns one active answer and its ETag. Deleted answers are absent from both reads. `POST /api/v1/posts/{postId}/answers` accepts `{ "bodyMarkdown": "...", "anonymous": false }` and returns `201 Created`, `Location: /api/v1/answers/{answerId}`, ETag `"v1"`, and the answer. `anonymous` is optional and defaults to false. `Idempotency-Key` may be supplied for a 24-hour matching retry; reusing a key with different content returns `409 idempotency_key_reused`.

An active `Answer` contains `id`, `postId`, `deleted: false`, `bodyMarkdown`, `contributors`, `anonymous`, `attachments: []`, `endorsedAt`, `endorsedBy`, `createdAt`, `updatedAt`, `version`, `canEdit`, `upvoteCount`, and `viewerUpvoted`. `contributors` is a distinct list of `{id,displayName}` editors of a named answer; deleted accounts are omitted. For an anonymous answer, `contributors` and `endorsedBy` are `null` to every student, including its contributors, and visible to TAs/instructors. `canEdit` is projected independently of contributor visibility.

`PATCH /api/v1/answers/{answerId}` accepts only `{ "bodyMarkdown": "..." }` and a current `If-Match`. The answer creator's course role at creation is the permanent minimum editing role: current students may edit student-origin answers, TAs may edit student- and TA-origin answers, and instructors may edit all answers. A higher-role edit does not raise that floor. Each successful editor is recorded once. The request atomically saves the Markdown projection, authoritative `Y.Text('content')` state, answer revision, and contributor. Insufficient role returns `403 permission_denied`; endorsed answers return `409 answer_endorsed`. Concurrent stale saves return `412` without changing the answer.

`PUT /api/v1/answers/{answerId}/endorsement` allows current TAs/instructors to endorse with `If-Match`, advances the answer version, and closes its Yjs document. Repeating with the current endorsed revision succeeds without another change. `DELETE /api/v1/answers/{answerId}` allows staff to delete an unendorsed answer with `If-Match` and returns `204 No Content`. An endorsed answer cannot be deleted (`409 answer_endorsed`).

## Question followups

Followups belong to questions, so a discussion can start before an answer exists. `GET /api/v1/posts/{postId}/followups` returns a page of direct followups and `meta: { total, nextCursor }`, where `total` counts root discussions. `GET /api/v1/followups/{followupId}/replies` returns one direct child page using the same shape. Both accept optional `cursor` and `limit` (1–100, default 20). `GET /api/v1/followups/{followupId}` returns one followup and ETag.

`POST /api/v1/posts/{postId}/followups` creates a root discussion. `POST /api/v1/followups/{followupId}/replies` creates a child of that followup on the same question. Both accept `{ "bodyMarkdown": "...", "anonymous": false }`, return `201 Created`, Location, ETag, and the new followup, and support 24-hour `Idempotency-Key` retry semantics. Current members may create roots and replies in active courses.

A `Followup` contains `id`, `postId`, `parentId` (null for a root), `author` (`{id,displayName}` or null), `anonymous`, `bodyMarkdown` (or null for a tombstone), `deleted`, `createdAt`, `updatedAt`, `version`, `canEdit`, `upvoteCount`, `viewerUpvoted`, and `replyCount`. `createdAt` retains microsecond precision for creation order. The author and staff see an anonymous author's identity; other students see `author: null`. Deleted accounts do not expose IDs. `PATCH /api/v1/followups/{followupId}` accepts only `{ "bodyMarkdown": "..." }` and `If-Match`. `DELETE /api/v1/followups/{followupId}` requires `If-Match` and returns `204`. Only the original author or current staff can edit or delete (`403 permission_denied` otherwise). A deleted parent with replies is retained as a bodyless tombstone for navigation; a deleted leaf is absent from ordinary reads.

## Upvotes

`PUT` or `DELETE /api/v1/answers/{answerId}/upvote` and `/api/v1/followups/{followupId}/upvote` add or remove the current member's vote and return the updated resource. PUT and DELETE are idempotent, including retries. A member may upvote their own content. At most one vote per member and target is stored. Votes update `upvoteCount` and `viewerUpvoted` but do not change the content version or ETag. Deleted or hidden content cannot be voted on; archived courses allow reads but reject vote writes.
