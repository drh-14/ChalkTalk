# Answers, followups, and upvotes

This document describes the implemented JSON text API. Every route requires a valid `__Host-chalktalk_session` cookie and current course membership. Unsafe requests also require an allowed `Origin` and `X-CSRF-Token`. Text requests require `Content-Type: application/json`; files use separate multipart parent-scoped routes described in the [OpenAPI attachment contract](../openapi.yaml). Shared answer, followup, and reply text is saved only through version-checked REST requests.

JSON success bodies use `{ "data": ... }` except paginated followup lists, which also include `meta`. Errors use `{ "error": { "code", "message", "requestId" } }`. Invalid JSON fields or a `bodyMarkdown` value outside 1–100,000 non-whitespace characters return `422 validation_failed`. Hidden, deleted, merged, absent, other-course, and nonmember resources return `404 not_found`. Inactive courses reject writes with `409 course_archived` while members may still read their content. Responses to individual versioned resources include `ETag: "vN"`. Conditional writes require the current `If-Match` (`428 precondition_required` if missing, `412 version_conflict` if stale). A note cannot have answers or followups (`409 not_a_question` on creation; `422 not_a_question` on listing).

## Shared answers

A question has at most one active `student` answer and one active `staff` answer. Students create the student slot; TAs and instructors create the staff slot. A second creation for an occupied slot returns `409 answer_kind_exists`. `GET /api/v1/posts/{postId}/answers` returns `{ "data": Answer[] }` with the student slot first. `GET /api/v1/answers/{answerId}` returns one active answer and its ETag. Deleted answers are absent from both reads. `POST /api/v1/posts/{postId}/answers` accepts `{ "bodyMarkdown": "...", "anonymous": false }` and returns `201 Created`, `Location: /api/v1/answers/{answerId}`, ETag `"v1"`, and the answer. `anonymous` is optional and defaults to false. New anonymous answers return `409 anonymous_posting_disabled` when the course disallows anonymity; prior successful idempotent retries still replay and existing anonymous answers remain readable and editable. `Idempotency-Key` may be supplied for a 24-hour matching retry; reusing a key with different content returns `409 idempotency_key_reused`.

An active `Answer` contains `id`, `postId`, `kind`, `deleted: false`, `bodyMarkdown`, `contributors`, `anonymous`, `attachments`, `endorsedAt`, `endorsedBy`, `createdAt`, `updatedAt`, `version`, `canEdit`, `upvoteCount`, and `viewerUpvoted`. `contributors` is a distinct list of `{id,displayName}` editors of a named answer; deleted accounts are omitted. For an anonymous answer, `contributors` and `endorsedBy` are `null` to every student, including its contributors, and visible to TAs/instructors. `canEdit` is projected independently of contributor visibility.

`PATCH /api/v1/answers/{answerId}` accepts only `{ "bodyMarkdown": "..." }` and a current `If-Match`. A student answer is editable by every current member. A staff answer snapshots its creator's TA or instructor role as its permanent minimum editing role: current TAs may edit TA-created staff answers, and instructors may edit all staff answers. A higher-role edit does not raise that floor. Each successful editor is recorded once. The request atomically saves Markdown, answer revision, distinct contributor, and append-only contribution event. A text edit clears the current endorsement while retaining its historical event; staff may endorse the revised answer again. Insufficient role returns `403 permission_denied`. Concurrent stale saves return `412` without changing the answer. The browser keeps independent unsaved drafts; a stale save shows the latest answer alongside the draft, and an explicit Overwrite retries the ordinary PATCH with the latest ETag. It is never an unconditional write.

`PUT /api/v1/answers/{answerId}/endorsement` allows current TAs/instructors to endorse with `If-Match`, advances the answer version, and records an append-only endorsement event. A historical empty answer cannot be endorsed (`409 answer_empty`); its next REST save must be nonblank. Repeating with the current endorsed revision succeeds without another change. `DELETE /api/v1/answers/{answerId}` allows staff to delete an unendorsed answer with `If-Match` and returns `204 No Content`. An endorsed answer cannot be deleted (`409 answer_endorsed`); editing its text first clears the current endorsement.

## Question followups

Followups belong to questions, so a discussion can start before an answer exists. `GET /api/v1/posts/{postId}/followups` returns a page of direct followups and `meta: { total, nextCursor }`, where `total` counts root discussions. `GET /api/v1/followups/{followupId}/replies` returns one direct child page using the same shape. Both accept optional `cursor` and `limit` (1–100, default 20). `GET /api/v1/followups/{followupId}` returns one followup and ETag.

`POST /api/v1/posts/{postId}/followups` creates a root discussion. `POST /api/v1/followups/{followupId}/replies` creates a child of that followup on the same question. Both accept `{ "bodyMarkdown": "...", "anonymous": false }`, return `201 Created`, Location, ETag, and the new followup, and support 24-hour `Idempotency-Key` retry semantics. Current members may create roots and replies in active courses. New anonymous roots and replies return `409 anonymous_posting_disabled` while the course disallows anonymity; prior successful idempotent retries still replay.

A `Followup` contains `id`, `postId`, `parentId` (null for a root), `author` (`{id,displayName}` or null), `anonymous`, `bodyMarkdown` (or null for a tombstone), `deleted`, `createdAt`, `updatedAt`, `version`, `canEdit`, `upvoteCount`, `viewerUpvoted`, `replyCount`, `attachments`, `resolved`, and `canResolve`. `createdAt` retains microsecond precision for creation order. The author and staff see an anonymous author's identity; other students see `author: null`. Deleted accounts do not expose IDs. `PATCH /api/v1/followups/{followupId}` accepts only `{ "bodyMarkdown": "..." }` and `If-Match`. `DELETE /api/v1/followups/{followupId}` requires `If-Match` and returns `204`. Only the original author or current staff can edit or delete (`403 permission_denied` otherwise). A deleted parent with replies is retained as a bodyless tombstone for navigation; a deleted leaf is absent from ordinary reads.

**Mentions:** Answer, followup, and reply bodies may [mention](notifications.md) course members. Creating or editing a body that mentions more than 20 people returns `422 too_many_mentions`.

**Resolving discussions:** A root followup is a discussion that is resolved or unresolved, and starts unresolved; replies report `resolved: false` and belong to their root. `PUT /api/v1/followups/{followupId}/resolution` resolves a discussion and `DELETE` on the same path reopens it. Both are idempotent, require CSRF protection, take no body, and return `200` with the followup and its unchanged `ETag`. Only TAs, instructors, and the question's author may change the state (`403 permission_denied` otherwise); `canResolve` tells the viewer whether they may. A reply returns `422 not_a_discussion`, a deleted or unreadable followup returns `404 not_found`, and an archived course returns `409 course_archived`. Changing the state changes neither the followup's `version` nor the question's `lastActivityAt`, so it does not reorder feeds or create unread markers or notifications. Creating a reply anywhere in a resolved discussion, at any depth, reopens it only while course resolution is enabled. When disabled, existing markers remain visible, `canResolve` is false, explicit resolve/reopen returns `409 followup_resolution_disabled`, and new replies do not clear markers.

## Upvotes

`PUT` or `DELETE /api/v1/answers/{answerId}/upvote` and `/api/v1/followups/{followupId}/upvote` add or remove the current member's vote and return the updated resource. PUT and DELETE are idempotent, including retries. A member may upvote their own content. At most one vote per member and target is stored. Votes update `upvoteCount` and `viewerUpvoted` but do not change the content version or ETag. Deleted or hidden content cannot be voted on; archived courses allow reads but reject vote writes.
