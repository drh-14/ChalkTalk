# Answers, followups, and upvotes

This document describes the **implemented text-only API**. Every route requires a valid `__Host-chalktalk_session` cookie and current course membership. Unsafe requests also require an allowed `Origin` and `X-CSRF-Token`. Requests with a body require `Content-Type: application/json`; multipart requests, attachments, and object-store integration are unavailable. Version-checked REST saves remain available alongside opt-in Hocuspocus/Yjs editing of answer and followup bodies.

All success bodies use `{ "data": ... }` except paginated followup lists, which also include `meta`. Errors use `{ "error": { "code", "message", "requestId" } }`. Invalid JSON fields or a `bodyMarkdown` value outside 1–100,000 non-whitespace characters return `422 validation_failed`. Hidden, deleted, merged, absent, other-course, and nonmember resources return `404 not_found`. Inactive courses reject writes with `409 course_archived` while members may still read their content. Responses to individual versioned resources include `ETag: "vN"`. Conditional writes require the current `If-Match` (`428 precondition_required` if missing, `412 version_conflict` if stale). A note cannot have answers or followups (`409 not_a_question` on creation; `422 not_a_question` on listing).

## Shared answers

A question has at most one active `student` answer and one active `staff` answer. Students create the student slot; TAs and instructors create the staff slot. A second creation for an occupied slot returns `409 answer_kind_exists`. `GET /api/v1/posts/{postId}/answers` returns `{ "data": Answer[] }` with the student slot first. `GET /api/v1/answers/{answerId}` returns one active answer and its ETag. Deleted answers are absent from both reads. `POST /api/v1/posts/{postId}/answers` accepts `{ "bodyMarkdown": "...", "anonymous": false }` and returns `201 Created`, `Location: /api/v1/answers/{answerId}`, ETag `"v1"`, and the answer. `anonymous` is optional and defaults to false. `Idempotency-Key` may be supplied for a 24-hour matching retry; reusing a key with different content returns `409 idempotency_key_reused`.

An active `Answer` contains `id`, `postId`, `kind`, `deleted: false`, `bodyMarkdown`, `contributors`, `anonymous`, `attachments: []`, `endorsedAt`, `endorsedBy`, `createdAt`, `updatedAt`, `version`, `canEdit`, `upvoteCount`, and `viewerUpvoted`. `contributors` is a distinct list of `{id,displayName}` editors of a named answer; deleted accounts are omitted. For an anonymous answer, `contributors` and `endorsedBy` are `null` to every student, including its contributors, and visible to TAs/instructors. `canEdit` is projected independently of contributor visibility.

`PATCH /api/v1/answers/{answerId}` accepts only `{ "bodyMarkdown": "..." }` and a current `If-Match`. A student answer is editable by every current member. A staff answer snapshots its creator's TA or instructor role as its permanent minimum editing role: current TAs may edit TA-created staff answers, and instructors may edit all staff answers. A higher-role edit does not raise that floor. Each successful editor is recorded once. The request atomically saves the Markdown projection, authoritative `Y.Text('content')` state, answer revision, distinct contributor, and append-only contribution event. A text edit clears the current endorsement while retaining its historical event; staff may endorse the revised answer again. Insufficient role returns `403 permission_denied`. Concurrent stale saves return `412` without changing the answer.

`PUT /api/v1/answers/{answerId}/endorsement` allows current TAs/instructors to endorse with `If-Match`, advances the answer version, and records an append-only endorsement event without closing the editable Yjs document. An empty live answer cannot be endorsed (`409 answer_empty`). Repeating with the current endorsed revision succeeds without another change. `DELETE /api/v1/answers/{answerId}` allows staff to delete an unendorsed answer with `If-Match` and returns `204 No Content`. An endorsed answer cannot be deleted (`409 answer_endorsed`); editing its text first clears the current endorsement.

## Question followups

Followups belong to questions, so a discussion can start before an answer exists. `GET /api/v1/posts/{postId}/followups` returns a page of direct followups and `meta: { total, nextCursor }`, where `total` counts root discussions. `GET /api/v1/followups/{followupId}/replies` returns one direct child page using the same shape. Both accept optional `cursor` and `limit` (1–100, default 20). `GET /api/v1/followups/{followupId}` returns one followup and ETag.

`POST /api/v1/posts/{postId}/followups` creates a root discussion. `POST /api/v1/followups/{followupId}/replies` creates a child of that followup on the same question. Both accept `{ "bodyMarkdown": "...", "anonymous": false }`, return `201 Created`, Location, ETag, and the new followup, and support 24-hour `Idempotency-Key` retry semantics. Current members may create roots and replies in active courses.

A `Followup` contains `id`, `postId`, `parentId` (null for a root), `author` (`{id,displayName}` or null), `anonymous`, `bodyMarkdown` (or null for a tombstone), `deleted`, `createdAt`, `updatedAt`, `version`, `canEdit`, `upvoteCount`, `viewerUpvoted`, and `replyCount`. `createdAt` retains microsecond precision for creation order. The author and staff see an anonymous author's identity; other students see `author: null`. Deleted accounts do not expose IDs. `PATCH /api/v1/followups/{followupId}` accepts only `{ "bodyMarkdown": "..." }` and `If-Match`. `DELETE /api/v1/followups/{followupId}` requires `If-Match` and returns `204`. Only the original author or current staff can edit or delete (`403 permission_denied` otherwise). A deleted parent with replies is retained as a bodyless tombstone for navigation; a deleted leaf is absent from ordinary reads.

## Upvotes

`PUT` or `DELETE /api/v1/answers/{answerId}/upvote` and `/api/v1/followups/{followupId}/upvote` add or remove the current member's vote and return the updated resource. PUT and DELETE are idempotent, including retries. A member may upvote their own content. At most one vote per member and target is stored. Votes update `upvoteCount` and `viewerUpvoted` but do not change the content version or ETag. Deleted or hidden content cannot be voted on; archived courses allow reads but reject vote writes.

## Live body editing tickets

`POST /api/v1/answers/{answerId}/collaboration-ticket` and `POST /api/v1/followups/{followupId}/collaboration-ticket` (for an existing root or reply) require the same session, current edit permission, allowed Origin, CSRF token, `Content-Type: application/json`, and an empty `{}` JSON body. A successful request returns `201 Created`, `Cache-Control: no-store`, and `{ "data": { "ticket": "…", "documentName": "answer:<uuid>" | "followup:<uuid>", "expiresInSeconds": 300 } }`. A ticket is bound to its document, user, and session, expires after five minutes, and can be consumed only once. Request a new ticket on every reconnect. Missing/invalid session returns `401`, insufficient role returns `403`, hidden/deleted/merged content returns `404`, and archived courses return `409`.

The browser connects to `/collaboration` with the ticket as its Hocuspocus token and the returned document name. Only `Y.Text('content')` can be edited. Each accepted Yjs update is persisted to PostgreSQL before the server applies or broadcasts it; later reads use the Markdown projection. Live text may be temporarily blank, unlike REST creation/PATCH. A text-changing live edit advances the content version, records answer attribution, and clears a current endorsement while retaining its historical event. Votes, creation of answers, root followups and replies, endorsement, and deletion remain REST operations. Existing root and reply bodies can be edited live. See the [WebSocket protocol](collaboration-websocket.md) for transport and failure behavior.
