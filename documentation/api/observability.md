# API observability

**Implementation status:** The Express API, dedicated background worker, and collaboration server expose private metrics when configured with a valid `METRICS_TOKEN`. The API and worker also emit sanitized JSON events. Local monitoring is token-driven; production requires the token and a spool directory at startup. This is an operator endpoint, not part of the browser `/api/v1` session API.

## `GET /metrics`

The API, worker, and collaboration server each serve a private `/metrics` route while observability is enabled. The worker serves only this route on its container port; it does not serve application requests. Send `Authorization: Bearer <METRICS_TOKEN>`; the token is distinct from user sessions and must be at least 32 characters when enabled. Invalid or missing tokens return `401` and no metrics. When disabled, the API route returns `404`, the worker does not start a metrics server, and the collaboration server does not expose metrics. Successful scrapes return Prometheus text (`200`); API and worker responses also set `Cache-Control: no-store`, and metric collection failure returns `503` on those routes. No browser CORS access is configured.

`chalktalk_http_requests_total` and `chalktalk_http_request_duration_seconds` use bounded method, Express route template, status class, and completed/aborted outcome labels; unmatched requests use `_unmatched`. The duration histogram includes a 0.2-second bucket. Health and metric scrapes are excluded from application request rates. `chalktalk_jobs_total` and `chalktalk_job_duration_seconds` use fixed `delete_course`, `delete_course_file`, `send_question_duplicate_email`, `digest_schedule`, or `digest_delivery` kinds and `succeeded`/`failed`/`canceled` outcomes for email delivery (other jobs retain success/failure). Process/Node metrics and log spool definite-drop, capacity-evicted-event, evicted-segment, and write-error counters are also exposed. No metric labels contain request URLs, query strings, request IDs, user IDs, course IDs, or content.

The API, worker, and collaboration registries also expose `chalktalk_db_pool_acquire_duration_seconds` and `chalktalk_db_query_duration_seconds` histograms with only a fixed `outcome=succeeded|failed` label; Prometheus adds the target `job` label. Acquisition time includes pool contention and connection setup. Query time is **client-observed**: it includes client queueing, network transport, PostgreSQL execution and locks, and result transfer. The dashboard's database attempt rate counts executed queries plus failed pool acquisitions; its failure fraction uses those same attempts, so connection failures without a query remain visible. Successful acquisitions are not counted again. Neither histogram isolates server execution or proves geographic network latency. Compare them with request duration and a VM-side database timing before changing the database region. There are no SQL, parameter, identity, or raw-error labels or per-query logs. The dedicated PostgreSQL LISTEN connection is outside these pooled-query metrics.

## Structured events

When observability is enabled, each application request completion/abort (excluding health and metrics scrapes) and job start/outcome is a JSON event to Docker stdout; API startup, database-pool errors, failed post-view writes, and unexpected server errors have separate event names. With observability disabled, startup and those system/error events still use a sanitized fallback logger, including unexpected worker failures; request and job events are not emitted. Events contain only a timestamp, severity, event name, and applicable request ID, method, matched route template, status, duration, completed/aborted outcome, fixed job kind and outcome, or bounded error code. The posts route may additionally include allowlisted post type/sort enums and a bounded result count on a successful post-list response. Authentication, account, and file-resource endpoints remain metadata-only. Passwords, tokens, emails, titles, Markdown, anonymous content, raw URLs, query strings, headers, file bytes, exception messages, and stack traces are never logged. Unknown routes have metadata only.

Each process also writes the same sanitized events asynchronously to its own named-volume NDJSON spool. Its 16 MiB segment size, 256 MiB total cap, and seven-day maximum age are finite: old unsent segments can be evicted, and the newest in-memory tail can be lost on a crash. The drop counter counts events rejected before persistence, including write failures. Capacity-evicted events are reported separately as **at-risk**, not confirmed loss: Alloy may already have sent them to Loki. Routine age expiry does not increase either event counter. An unavailable collector or disk does not block application requests. This is not a lossless audit log. An interrupted send near a restart may replay an event; persistent Alloy file positions prevent ordinary restart replay, not exactly-once delivery.

Both local and production Alloy tail the API and worker's sanitized spools through read-only mounts, persist file positions in a named volume, and send to Loki. Alloy has no Docker socket access, and neither Alloy nor Loki publishes a host port. Loki stores logs in a filesystem-backed TSDB with seven-day compactor retention; both spools expire segments older than seven days, and Prometheus retains samples for 15 days. Loki age retention does not cap bytes, and compaction/deletion may lag. Local API and worker Docker stdout uses the `local` driver with five rotating files of at most 20 MiB each per container; production Docker stdout uses three rotating files of at most 10 MiB. These copies are size/count-bounded rather than age-bounded, so `docker compose logs` may show events older than seven days. Existing Elasticsearch/Logstash volumes from older local stacks are left untouched and are not migrated. Production Grafana binds only to VM loopback and is reached through an SSH tunnel; see the [production guide](../../deployment/production/README.md#operate-and-verify).
