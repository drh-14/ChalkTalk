## Decisions

### 1. Thin shell entrypoint, explicit local orchestration

`deployment/local/start.sh` locates its directory/repository independently of caller cwd and performs deterministic static validation using Docker/Compose and standard shell tools only (POSIX shell, awk/sed/grep, filesystem/temp-file utilities). No host Node, npm, installed application dependencies or AWS SDK is a deployment prerequisite. Application dependencies and the approved SES SDK are used inside containers in phase 2. Prefer a small restricted shell parser over sourcing/eval, a host runtime, or a configuration framework. Repository development/test commands can still require Node; that is not a startup requirement.

Phase 1 validates syntax, required fields, topology/conflicts, supported URL grammar, ports and credential MODE, not whether credentials are valid, permitted, reachable or expired. No SDK/provider resolution, credential-source probing or external request occurs here. It may perform a read-only Compose render after original-input validation; suppress secret-bearing output/errors. Static invalidity means zero build, pull, create, start, migration, bucket or provider request. Phase 2 runs bounded runtime checks in containers using app dependencies after container creation, but before serving traffic or claiming worker jobs and before any provisioning not explicitly authorized by ownership/consent.
Proposed interface: `start.sh [--env-file PATH] [--project-name NAME] [--ack-external-migrations]`. Unknown/duplicate options fail. Default env file is `deployment/local/.env`; relative explicit paths resolve from caller cwd and are canonicalized once. Project default remains `chalktalk`; override must be explicit (not inherited `COMPOSE_PROJECT_NAME`). No stop/reset/delete flag is included.

For supported application/operator configuration, explicit selected file values win over parent values; absent file values may use parent values, then documented non-secret defaults. An explicit blank is not absence for required fields/flags. Parse a deliberately restricted literal `KEY=value` file: keys match `[A-Z_][A-Z0-9_]*`; allow blank lines and whole-line `#` comments; split on the first `=` and preserve the literal value (including subsequent `=`). Empty values are parsed but may fail field validation. Nonempty values use printable ASCII, no leading/trailing whitespace, quotes, backslash, dollar expansion or backticks. Interior spaces are literal (for sender display names); `#` inside a value is literal, never an inline comment. Reject CR/NUL, multiline/continuations, duplicate keys, `export`, shell assignment syntax, quoting, substitution/interpolation and malformed lines rather than attempting shell/dotenv compatibility. Never `source`, `.`, or `eval` operator input, nor construct a command string from it. Reject unsupported literal syntax with variable/line guidance without echoing values; use supported literal values or percent-encoding in URL components, not escaping or shell expressions. Apply the same value/field checks to supported inherited inputs.

Ambient `COMPOSE_*` controls cannot select files/project/profiles. Validate merged original input before generating internal connection settings, with shared acceptance/rejection fixtures constraining shell and app validators. Never mutate the source env file. A stale root `.env` is neither implicitly loaded nor overwritten; document explicit upgrade/selection. Generated runtime configuration must preserve literal values under Compose parsing and cannot reintroduce interpolation.
Use explicit `--project-directory`, `--project-name`, `--env-file`, and ordered `-f` arguments for every Compose invocation and clear inherited Compose controls (including file/profile/project/env discovery). Do not expose arbitrary `--compose-file` passthrough. Base config contains application/gateway/monitoring; launcher selects small database/store overlays and optional loopback port overlays under `deployment/local/` (no implicit override file discovery). Remove dependencies on omitted data services in the base model; startup sequencing gates applications on successful database/storage preparation. `docker compose config --format json` is a read-only validation seam, but never print its secret-bearing result. Preserve all existing volume keys and default project, including PostgreSQL, SeaweedFS and Caddy CA. Application source mounts remain current local-development mounts.

### 2. Original operator inputs and resolved runtime inputs are distinct

The launcher owns flags; applications receive concrete connections, not flags or the raw operator env file. Build a minimal allowlisted runtime environment rather than pass-through `env_file` containing conflicting operator settings. Secret-bearing temporary env/Compose files for original explicit inputs and derived connections, if needed, are mode 0600, ignored, cleaned on exit, and never logged or passed as URL-bearing process arguments. Never write resolved SES default-chain credentials to these files or environment variables. Do not commit runtime output. Avoid `set -x`, raw parser/SDK causes, and `compose config` dumps.

Input inventory (populated means non-whitespace; invalid blank required values still fail):

| Selection | Required original inputs | Conflict/fallback rule |
| --- | --- | --- |
| Bundled DB (default) | `LOCAL_DATABASE_USER`, `LOCAL_DATABASE_PASSWORD`, `LOCAL_DATABASE_NAME` (safe documented development defaults allowed) | Any populated `DATABASE_URL` fails; this is the only current supported external DB connection input. Encode user/password/database safely when constructing internal URL. |
| External DB | `DATABASE_URL` | Require the documented supported postgres/postgresql URL grammar, host, user/password and database; reject malformed/unsupported URL, fragment, invalid port, contradictory TLS parameters statically. No local fallback or production Supabase-host restriction in local mode; never disable requested TLS verification. |
| Bundled store (default) | `LOCAL_OBJECT_STORE_ACCESS_KEY_ID`, `LOCAL_OBJECT_STORE_SECRET_ACCESS_KEY`, `LOCAL_OBJECT_STORE_BUCKET`, `LOCAL_OBJECT_STORE_REGION` | Any populated `S3_ENDPOINT`, `S3_BUCKET`, `S3_REGION`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`, or `S3_SESSION_TOKEN` fails, even alone. |
| External store | All five `S3_ENDPOINT`, `S3_BUCKET`, `S3_REGION`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`; optional `S3_SESSION_TOKEN` | Explicit S3 pair only; generic AWS credentials never fill missing S3 fields. Accept HTTP/HTTPS S3-compatible endpoints, reject userinfo/query/fragment and malformed URLs; HTTP support remains for private local-compatible stores, not mail. |

The template documents local defaults only in `LOCAL_*`; it must not populate external fields by default. Local flags accept exactly lowercase `true`/`false`; supplied blank is invalid. Proposed optional `LOCAL_DATABASE_HOST_PORT` and `LOCAL_OBJECT_STORE_HOST_PORT` accept canonical decimal integers 1..65535, omitted means unpublished. Reject use for disabled services and duplicate selected host bindings; bind `127.0.0.1`, never an operator-supplied wildcard host. Retain current `WEB_PORT`, `GRAFANA_PORT`, domain, proxy, auth/metrics secrets and frontend derivation validation. Reject known template placeholders for required secrets; do not invent a password policy for external credentials. Validate static shared app settings and embedding config grammar before deployment mutation too; defer credential/network validity to phase 2. Failure diagnostics identify setting names and remediation, never values/URLs/raw causes. Reserved local resolved values cannot be injected via raw env to bypass preflight.

### 3. Mail selection and credential boundary

Local `EMAIL_PROVIDER` and `EMAIL_FROM` are required; validate sender as one mailbox with optional display name, reject CR/LF/header injection. Exactly one recognized provider namespace may be populated. Recognized set: Resend `RESEND_API_KEY`, `RESEND_API_BASE_URL`; SendGrid `SENDGRID_API_KEY`; SES `SES_REGION`, `SES_CREDENTIALS_MODE`, `SES_ACCESS_KEY_ID`, `SES_SECRET_ACCESS_KEY`, `SES_SESSION_TOKEN`; legacy SMTP `SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURE`, `SMTP_USER`, `SMTP_PASSWORD`, `SMTP_FROM` are forbidden launcher inputs. Known arbitrary SMTP/gateway/origin selectors must fail rather than be translated. No extra provider-specific configuration keys are introduced implicitly.

Normal startup uses official HTTPS endpoints, no custom mail origin. Existing controlled Resend endpoint tests retain isolated injection; HTTP mocks are not operator delivery configuration. Selected Resend origin override, if present, must equal the official HTTPS origin. SendGrid uses its fixed HTTPS mail-send endpoint; SES uses the SDK's regional HTTPS endpoint. No new SendGrid dependency: use existing Node fetch. Use approved `@aws-sdk/client-sesv2` for SES; choose the version at implementation time from actual Node 22/API SDK/lock compatibility (existing S3 dependency is `^3.1150.0`), update only required lock entries, record exact resolved version and checks. No package install/change in planning.

SES explicit mode uses only the original SES-prefixed pair/token and explicit region; generic AWS credentials do not override them. Explicit temporary credentials remain operator-renewed; expiry/authorization is a runtime condition, not a static syntax check. Default-chain mode rejects every populated SES credential field, retains explicit `SES_REGION`, and retains the SDK credential PROVIDER FUNCTION in each sending container so later sends can refresh credentials. Never resolve once and replace the provider with a credential object, export resolved credentials to env files, serialize them to another container, or persist them in queue snapshots. A dedicated runtime preflight container may resolve its own provider read-only; API and worker still initialize their own refreshable providers from the same explicitly supplied sources.

The operator explicitly supplies narrowly scoped, container-accessible read-only credential/config/profile or web-identity token files, or an explicitly configured reachable workload-role source (standard AWS credential environment inputs also remain supported). Expose only selected source paths to the sending/preflight containers as read-only files, never the home directory; use fixed container paths and existing AWS source-selection variables, not arbitrary Compose passthrough. Any helper/configuration under a mounted profile must be supported and available inside the container; do not execute arbitrary credential-process commands from operator configuration as an automatic host bootstrap. Source availability, profile validity and network/permission errors are bounded phase-2 checks. No automatic home mounts, host networking, metadata exposure or credential harvesting. Disable unintended metadata discovery unless the operator explicitly selects an accessible workload-role source; do not make an inaccessible host source reachable by widening network access. Static validation checks configured source grammar/mode, not source credential validity. SDK source resolution and refresh errors are sanitized; no default-chain result crosses the container boundary.

Generic `AWS_*` inputs remain independent of local/external S3 conflict handling, and are not another mail provider. Document explicit source wiring and the operator's responsibility to keep token/profile sources accessible and refreshed. A successful credential resolution is not proof of SES send permission or inbox delivery; do not send test mail or provision resources as a permission probe.
Production environment branch continues Resend-only/fixed sender/official origin and Supabase TLS/storage validation. Tests and direct API fixtures can continue explicit isolated test transports; there is no new public production bypass selector. Keep historical SMTP snapshot decoding only for safe cancellation/compatibility, not a local deployment send option.

### 4. Existing email seam and durable queue, not a replacement

Extend `Environment.email`, `EmailSender.provider`, frozen-email provider decoding and `createEmailSender`. Add focused adapter modules only if that keeps `auth/email.ts` cohesive. Prepare SendGrid JSON and SES v2 raw MIME before commit, retaining exact bytes/attachments/CIDs/from across retries. Existing nodemailer can compile MIME without opening an SMTP connection. SDK transport/auth signing can vary per attempt, but frozen provider message content cannot. SES v2 and SendGrid acceptance must be validated (SES message ID; SendGrid successful accepted response), not merely any resolved request.

Bound external attempts to the existing 30 seconds and abort signal; avoid SDK hidden retry multiplication (one observable handoff per worker attempt, configure SES client maxAttempts accordingly). Reuse typed quota/configuration/permanent delivery errors and existing jobs backoff/max-attempt policy. Map 429/throttling, auth/config, timeout/network/5xx, malformed success and permanent payload failures explicitly; never store raw body/header/SDK messages. Persist safe provider/category codes in `last_error`; frozen content stays only in its existing protected JSON snapshot until success/cancellation. No promise that a successful provider response means inbox receipt. Resend keeps stable idempotency; SendGrid/SES ambiguity may duplicate.

Preserve locks/revalidation through send, current content/access/address/sender checks, opt-out timing, snapshot-before-handoff, cancellation erasure, and immediate auth mail (verification/reset) outside durable queue. Sender mismatch already cancels in `worker.ts`; extend rather than weaken that check. Existing JSON storage likely needs no new queue schema migration; verify against database reference before implementation.

### 5. Database and bucket lifecycle gates

Phase 1: parse restricted literals → validate every original static input and credential mode → derive private internal connection settings → read-only explicit Compose render with no secret output. Supported URL grammar must be executable in shell and app validation: anchored supported schemes, DNS/IPv4 or bracketed IPv6 host, optional canonical port, valid percent escapes, no controls/whitespace/fragment; PostgreSQL requires one user/password/database and documented noncontradictory TLS query options; S3 endpoint forbids userinfo/query/fragment but allows a service path. Reject unsupported grammar instead of accepting a shell parser/app parser disagreement. Cover reserved characters/percent escapes, IPv6, duplicate query keys and malformed ports with common fixtures. Validate configured HTTPS mail origins, sender and ancillary app settings statically too. No credential/network/schema probing in phase 1, and no build/pull/create/start/migration/bucket/provider request for any static failure.

Phase 2 after valid static input: build/pull required images → create/start selected data and runtime-check containers → wait for health → bounded containerized configuration/credential resolution and read-only connectivity/schema/bucket checks → ownership/consent-authorized migration/bucket preparation → recheck readiness → enable traffic and workers. All required runtime checks gate application traffic and worker claims; image/container creation is allowed before these checks finish. Separate read-only checks from provisioning so an unavailable credential source or failed check cannot accidentally trigger an external migration/create-bucket. Runtime checks cannot prove provider send permission without a send; defer remaining provider permission failures to sanitized existing immediate-mail/queue failure handling, never automatic test sends. Static accepted configuration with rejected credentials or unavailable network/schema fails phase 2, not a retroactive zero-container guarantee. Never perform unauthorized schema/bucket provisioning, destructive cleanup, volume removal/reset, or automatic retries that broaden authority on failure. Valid authorized preparation may have completed before a later failure; retain data and report its safe status.

Do not use `runMigrations` for external no-ack status: it creates the ledger. Add a read-only migration-status seam that reads filesystem inventory, tests ledger existence via catalogs, and lists missing migrations without DDL. Missing ledger is pending, not permission to bootstrap. Explicit `--ack-external-migrations` is invocation-only, never sourced from env or cached. With acknowledgment use existing locked/transactional ordinary runner and special answer-projection safeguards. External semantic extension/table/index provisioning remains a separate documented manual command/prerequisite; check it read-only when embedding is configured and fail with guidance if absent. Without embeddings, ordinary full-text/fuzzy behavior remains available.

For bundled DB, ordinary then semantic tracked execution under appropriate locks/transaction; record semantic SQL version in a separate semantic ledger namespace/table so ordinary migrations/inventory are not incorrectly reported pending for external DBs. New bundled DB runs semantic DDL once. Existing compatible objects can be validated and recorded/adopted, never dropped/recreated to force parity; mismatch fails actionably. Use explicit transaction around the existing xact advisory lock. Version/checksum semantic SQL so later drift is visible, not silently rerun. Tracking/compatibility rules must have real PostgreSQL tests.

Bucket checks run in phase 2 only after all original static inputs validate. A local-only preparation operation creates bundled bucket if missing; API/worker startup only verifies a resolved external bucket and never infers creation permission from `!production` or endpoint presence. Preserve production's existing fail-if-missing behavior. Pass ownership only to the provisioning step, not topology flags to ordinary app services.

## Risks / Trade-offs

- Shell/app validators can drift → restricted supported grammar and executable shared acceptance/rejection fixtures; no host Node fallback.
- Credential sources may expire/become unreachable → retain SDK provider functions and test refresh in long-running sending containers; explicit temporary credentials require operator renewal. No resolved-credential export or persistence.
- Runtime validity cannot be determined by static parsing → container creation is allowed in phase 2; readiness/worker/provisioning gates and redacted errors preserve the approved authority boundary.
- Existing local root `.env` has conflicting old defaults → provide explicit upgrade instructions; do not rewrite/copy it automatically or silently discard conflicts.
- Changed local DB credentials do not rewrite initialized PostgreSQL volumes → fail health/auth actionably and explain operator-managed credential repair, not reset.
- External service network/authorization failures cannot be fully predicted statically → gate app startup, redact failures; zero-mutation promise is for invalid static configuration, not rollback of phase-2 runtime failures.
- Ambiguous SendGrid/SES acceptance → durable identical retry and explicit duplicate risk, not exactly-once claims.
- Shared config/queue code affects production → positive/negative production regression tests plus unchanged deployment diff; no production files required.
- Parallel user changes → recheck branch/base/diff at apply time; preserve UI271/docs272 and do not transplant archived deployment commits wholesale.
