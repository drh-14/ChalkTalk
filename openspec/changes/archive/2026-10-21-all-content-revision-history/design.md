## Context

See proposal.md for motivation and the new `content-revision-history` spec for behavior. `PostService`, `AnswerService`, and `FollowupService` currently perform PostgreSQL-backed REST saves with resource `version`/`ETag`; answer editing is save-only, not Yjs. `apps/api/src/http/app.ts` owns routes. Private post access is checked via `canReadPost`; answers/followups inherit parent visibility. Posts can become confirmed duplicate sources, and deleted posts/followups retain scrubbed tombstones. Course deletion explicitly removes child rows in `apps/api/src/jobs/worker.ts`. Existing public contracts are in `documentation/api/posts.md`, `documentation/api/answers.md`, `documentation/openapi.yaml`, and `documentation/database.md`.

## Goals / Non-Goals

**Goals:** Atomic, immutable text snapshots; no identity leak from anonymous/private content; restore through the existing optimistic-concurrency seam; predictable purge and deployment behavior.

**Non-Goals:** Realtime collaboration, file/attachment snapshots, audience or moderation rollback, historical activity reconstruction, or resurrecting a deleted resource.

## Decisions

1. **Use one typed revision table, not per-resource shadow tables or JSON event sourcing.** Migration `047` (reservation only; implementation must check latest migration before naming) adds `content_text_revisions` keyed by UUID, `course_id`, content kind (`post`, `answer`, `followup`), resource ID, ordinal, captured resource version, created timestamp, nullable editor user ID, title/body text, nullable restored-from revision ID, and baseline flag. Unique `(kind, resource_id, ordinal)` and lookup index cover ordered history; check constraints enforce title for posts and body shape. Store only text and provenance, not a full resource projection. A nullable editor supports baseline and deleted-account redaction. Foreign-key strategy must allow deletion purge without cross-type FK impossibility: explicit same-transaction deletes on soft deletion and a course FK with `ON DELETE CASCADE` or explicit course-worker cleanup. Considered three tables for stronger FK typing; rejected repeated API/data handling for the same immutable shape. **Security condition:** reject cross-resource revision IDs in the service, never infer visibility from a revision row alone.

2. **Capture at existing transaction boundaries.** On create, insert initial snapshot with the content row. On save, compare persisted title/body or body against requested text after authorization and ETag checks; append one snapshot only for an actual text change, including text-changing restore. Nontext updates may advance the resource version without adding a text revision. Leave creation/revision ordinals independent of parent `version`. Existing answer content-change logic clearing current endorsement and preserving endorsement events applies to restore. Existing post text edit activity behavior applies; followup/answer activity and notification behavior follow their normal text-save paths, avoiding a second restore-specific notification model. Considered triggers, but application transactions expose editor, restore source, and authorization more clearly; direct SQL mutation paths should be covered by tests/audit.

3. **Backfill a single baseline for every active, readable text row.** The migration snapshots only nondeleted posts, nondeleted answers under active/unmerged posts, and nondeleted followups under active/unmerged posts. Confirmed merged sources also retain original text and need baseline so unmerge exposes history; therefore include nondeleted merged sources and their live children while suppressing API reads until unmerge. Do not invent historical editor or timestamp; use migration capture time with `baseline=true`, preserve the row's then-current `version`, and describe this in UI. Run in bounded batches if data volume demands it, with uniqueness/idempotent insertion for safe retry. New writes after migration always create their own initial snapshot. Considered backfilling from `updated_at` and `author_user_id`; rejected because neither proves when/current text was first written or who last edited it.

4. **Use type-specific REST paths and one shared authorization/capture service.** Add GET list, GET one, GET compare (two IDs), and POST restore under `/api/v1/posts/{id}/revisions`, `/api/v1/answers/{id}/revisions`, and `/api/v1/followups/{id}/revisions`; replies use the followup route. The common service first resolves the current parent through existing visibility rules and course membership, then loads revisions constrained by kind/resource ID. Read in archived courses; restore checks active course, staff role, current ETag, and existing text validation. Standard `{data}` envelope, existing error codes, no-store cache. Compare returns two full text states (UI computes display diff), avoiding a new diff dependency. Restore returns normal updated resource and ETag. A separate endpoint rather than adding history to every content response limits payload and accidental exposure.

5. **Scrub on deletion and redact dynamically.** In each individual soft-delete transaction delete its revision rows; post deletion also deletes nested answer/followup revisions. Course deletion worker removes all revisions before content rows. Tombstone and merged-resource history requests return 404; retained merged revisions become available after unmerge. Editor projection is computed per request: anonymous content exposes editor IDs/names only to current staff; deleted account has null ID. Do not cache a per-viewer projection globally. Foreign keys must avoid preventing existing hard-delete jobs.

6. **One history UI pattern for posts and nested discussion.** Reuse existing content detail authorization/projections and clients in `apps/web/src/posts` and `apps/web/src/answers`; lazily fetch history when opened. Show baseline label and revision times, select two revisions for comparison, and require staff confirmation for restore. On 412 retain the selected revision and offer refresh/retry; never silently force an overwrite. Use semantic controls, keyboard operability, and text labels for additions/deletions rather than color alone.

## Risks / Trade-offs

- [Concurrent save and backfill] → Migration acquires appropriate row/transaction ordering or deploys schema/backfill before enabling revision-writing code; idempotent unique baseline prevents duplicates. Verify final migrated text equals the saved row at the chosen cutover.
- [History disclosure after membership or audience change] → Resolve the current parent and role on every request; query revisions only after that check; `private, no-store` responses.
- [Orphaned old text on soft deletion or course hard deletion] → Same-transaction purge plus migration/worker integration tests; no retained content in tombstones.
- [Large histories] → Paginate list metadata and lazy-load selected bodies if needed; ensure deterministic ordering and bounded limits. Do not truncate stored text.
- [Migration ordering collision] → `047` is conceptual only; inspect upstream migrations immediately before implementation and choose the next free number.

## Migration Plan

1. Add table and indexes with baseline backfill, followed by transactional service capture and API/UI rollout. Coordinate deployment so writes cannot occur between baseline and capture activation without snapshotting; a single maintenance/deploy boundary or catch-up backfill handles that interval.
2. Verify row counts and sample current-text parity before enabling read/restore UI; exercise deletion and archived/merged/private cases.
3. Rollback application code can stop exposing history without removing the table. Do not automatically down-migrate the table, since that irreversibly discards audit data. If rollback of schema is required, explicitly export/retain history first and obtain a separate deletion decision.
