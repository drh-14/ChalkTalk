## Context

Merged PR #67 stores `posts.private` and author-or-current-staff visibility. The same boundary is enforced in several SQL queries and in post descendants, attachments, notifications, digest, and collaboration; it is not yet a general audience relation. The unpublished `3a1bdf0` commit explored selected-staff access and exposed live-transport and concurrent membership-change races, but predates the merged private-post schema. Its logic and tests are a source to review, not a commit to apply wholesale. See `proposal.md` and `specs/post-audiences/spec.md` for the agreed behavior.

## Goals / Non-Goals

**Goals:** One fail-closed authorization rule at every post and parent-content seam; consistent current membership under concurrent changes; backward compatibility for existing `private` clients and rows; predictable group lifecycle; no content leak through live transport.

**Non-Goals:** Changing course-statistics semantics, per-course policy switches, notification preferences, folders, polls, revision history, or existing editing architecture. No new external service or dependency.

## Decisions

1. **Persist one audience identity, not several independent privacy flags.** Extend posts with an audience discriminator and nullable group reference, plus a normalized selected-staff recipient table. Backfill `private=false` to `class` and `private=true` to `staff`; retain `private` as a compatibility projection/request alias while making the new audience relation authoritative. Add database constraints for valid combinations and class-only polls/announcements. An alternative of piling group and recipient columns beside a writable `private` boolean creates contradictory states and difficult SQL predicates.
2. **Separate staff-managed group membership from course membership.** Store course-scoped group and membership rows with uniqueness and same-course validation. Only current course members are eligible group members. Group read access is the intersection of current course membership and current group membership; neither authorship nor course-staff management bypasses that intersection. A referenced group uses a restrictive delete guard, including active posts; rename does not change access. Course/account deletion cleans up dependent rows. An alternative of copying group members into each post at creation violates the approved current-membership behavior.
3. **Centralize the audience predicate and authorize before projection.** Replace scattered `NOT private OR author OR staff` logic with one shared SQL predicate and a service-level assertion for direct operations. Use it before list ranking/pagination/counting, response projection, idempotent replay, duplicate redirects, attachments, notifications, and session access. Keep unauthorized-ID behavior indistinguishable from absent IDs (`404`). Do not rely on web visibility controls for security. Selected recipients must still currently hold TA/instructor role. A general staff override is expressly rejected.
4. **Handle revocation races at the data and transport seams.** Validate selected recipients and group membership in the creation transaction; serialize eligibility with membership/group updates using a consistent lock order, and recheck in read/write operations. The live session adapter must check current parent read/write permission for each incoming message and outgoing frame, including awareness, replay, buffered messages, and end notifications; failed, timed-out, or over-buffered authorization closes the connection without flushing private data. Review the tested approach in `3a1bdf0`, adapting it to current code rather than restoring its obsolete migration. Polling or notification-only socket invalidation is insufficient if revocation notices fail.
5. **Preserve private lifecycle and delivery defaults.** Existing private-to-class publish remains conditional and one-way; only an author who still has access or currently authorized staff may publish. Restricted posts remain ineligible duplicate targets and out of all daily digests. Notification insertion and delivery recheck audience access. Existing aggregate statistics behavior remains as merged; this PR does not add a new statistics privacy policy. All generated attachment links are gated at request time; already-issued external URLs have their existing bounded lifetime.
6. **Expose explicit audience APIs and UI while retaining old clients.** Extend create/projection contracts and add course-scoped group CRUD/membership endpoints using existing authentication, CSRF, role, and error conventions. `private: true` maps to `staff` when no explicit audience is supplied; conflicting `private`/audience combinations fail validation. The composer permits a group only while the poster is a current member and presents only eligible selected staff. Detail and feed labels use the returned audience; client-side controls are advisory, with server rejection preserved on a membership race.

## Risks / Trade-offs

- **[Privacy regression in a forgotten seam]** → Inventory every direct and descendant endpoint plus worker query; write real-PostgreSQL tests at public HTTP/job seams and a live-transport revocation test before implementation. Include search, counts, attachment downloads, and existing notifications.
- **[Concurrent group/role removal leaks content]** → Use transaction-safe authorization and egress checks rather than cached role/group state. Reproduce membership races in integration tests where practical.
- **[Backward compatibility between `private` and `audience`]** → Map legacy requests explicitly, test conflicting combinations, migrate rows deterministically, and document both fields before any deprecation.
- **[Unavailable authorization slows live transport]** → Fail closed with bounded queue/deadline rather than send from a stale permission cache; verify authorized sessions continue normally.
- **[Overlapping feature PRs change migration numbers or post contracts]** → Reserve `044` only conceptually; choose the next unused number and rebase/test against the final target head. Keep this as an independent PR, not a stacked feature branch.

## Migration Plan

1. Rebase onto the final target main; choose the next unused migration number (planned `044`). Add groups, group memberships, selected recipients, audience field/constraints/indexes, and backfill from `posts.private` in one transactional migration.
2. Deploy API capable of reading migrated rows and accepting both old `private` and new audience shapes; update dependent services and web client in the same release. There is no period where narrowed posts may be served by the old staff-wide predicate.
3. Roll back application code only if no selected-staff/group posts have been created; otherwise forward-fix to avoid re-exposing restricted posts. Do not drop audience data on an ordinary rollback.
