## Goals / Non-Goals

Prove identified application boots stopped their own work safely and durably, with a small lifecycle module and explicit owner adapters. Preserve ordinary API/database semantics, queue fences, email idempotency limits and existing reconnect behavior. No replacement automation, backup/cutover, data migration, global settings, real mail or production commands here. No receipt claim covers dashboards, scripts, other deployments or all writers in the world. No promise for unsent browser edits, crash recovery before drain, DB/S3 atomicity or exactly-once mail.

## Decisions

### 1. Cohesive lifecycle module and irreversible state

Proposed files `lifecycle/runtime.ts`, `lifecycle/evidence.ts`, `lifecycle/types.ts` hide signal/deadline/accounting mechanics behind a small interface: synchronous `admit(kind)` returning an idempotently released work lease or rejection; `markRunning()` guarded by current state; `fail(code)` for sticky unresolved failures; one `shutdown(trigger)` promise; read-only readiness/state and force-cancel signal. Internal seams accept monotonic clock, filesystem and exit adapter for deterministic tests. Avoid a plugin registry or universal task framework.

State is STARTING -> RUNNING -> DRAINING -> STOPPED or FAILED. STARTING may enter DRAINING without RUNNING. A fatal error drains with failure latched; no state returns to RUNNING. Install signals/fatal handlers before any asynchronous bootstrap, and count each startup operation before awaiting it. Check state before and after each awaited startup step; a late result must be closed, never open a listener/start a poll. Register resources at creation so partial startup can unwind. Repeated SIGTERM/SIGINT joins one promise and never extends the first monotonic deadline (120,000 ms). Wall timestamps are evidence only, not timeout clocks.

At first transition synchronously disable business admissions, readiness, upgrade/edit admissions and claim/scheduler entry. Record cutoff; do not await filesystem reads first. Expected validation/authorization failure or confirmed durable retry is not automatically a process failure. Unresolved persistence/cleanup, uncertain external effects, lost ownership and fatal errors are failure. Fatal handlers do not continue normal operation. A recoverable collaboration store error may clear only when the final exact frozen document save is confirmed; no broad resetting of failure flags.

### 2. Ownership, HTTP and thread-live

Track before asynchronous auth, pool acquisition, SQL claims, LISTEN setup, S3 calls or service invocation. A lease follows actual operation completion, not response `finish`/`close`, socket disconnect, Promise.race timeout or a finally that merely launched work. Nested required operations must settle before releasing their owner. Use a focused async route wrapper/admission adapter around existing handlers; wrapping Express `next()` alone does not await downstream work. Audit detached service promises and compensation catches within affected routes; expose only outcomes needed by this contract, not a wholesale HTTP rewrite.

`GET /ready` returns 200 `{ "ready": true }` only in RUNNING, otherwise 503 `{ "ready": false }`; `Cache-Control: no-store`; no IDs, phase details, counts, secrets or dependency diagnostics. Serve equivalent probes on collaboration and on the worker's existing metrics HTTP port (also when observability is disabled); avoid another port. Preserve API `/health` 200 `{ "status": "ok" }` while its listener lives; role probes mean process liveness, not durable-drain proof. Probe routes bypass business admission, parsing, authentication and DB. Unsupported readiness methods cannot mutate lifecycle. During final transport closure probes can become unreachable; liveness is not promised after listener closure.

After cutoff new business requests, including existing keep-alive/pipelined requests and OPTIONS, get 503 with `Retry-After: 1`, `Connection: close`, `Cache-Control: no-store` and a generic `service_unavailable` error in the existing error envelope. Apply before parsers/auth/rate-limit/storage side effects; preserve configured-origin CORS headers needed to read the response without opening access. Upgrades denied before async auth get HTTP 503 with Retry-After/connection-close. Previously admitted auth must settle but cannot register a new socket after cutoff. Close idle connections; close listening transports after admission is disabled. In-flight uploads/downloads continue until handler, stream, S3, commit/rollback, required compensation/temp cleanup settle. Disconnected clients do not decrement active handler accounting.

Thread-live stops new inbound callbacks and reconnect timers, awaits pending auth/messages/notifications/startup callbacks, closes clients and awaits close callbacks, UNLISTEN/end and listener teardown before pool closure. A callback already admitted may finish; late callback cannot start new application work. No detached retry can reopen LISTEN after drain. Transport close alone is not settlement.

### 3. Collaboration freeze then confirmed save

Freeze edit admission synchronously at cutoff, including already connected sockets. Count handlers before async authorization. A handler admitted before cutoff may finish applying its authorized edit; a later frame, including one merely buffered in transport, may not apply. Settle admission transactions (rollback if socket cannot register), authorized pre-cutoff handlers, lifecycle notification/sweep callbacks and stores, preventing new timers/reconnects/idle-end actions. An already admitted user-requested end may complete according to its existing contract; shutdown itself must not manufacture an end.

After handlers settle, capture a final frozen version/encoded Yjs state for every loaded document (connected or disconnected), serialize against pending/debounced stores, and await a confirmed database save of that exact final state and projection. Rejected allSettled entries must be classified/propagated. Hocuspocus flush/destroy callbacks are not proof of successful storage; destruction cannot precede confirmation. Prevent an older delayed store from overwriting the final state. Only then destroy/unload documents, close sockets and await disconnect touch/abort/store callbacks and LISTEN teardown; no callback may mutate document state after freeze or dirty the final save. Keep pool open through required callbacks. If implementation of installed Hocuspocus cannot enforce this ordering with existing hooks, stop for a concrete design review rather than assuming it can.

Do not set lifecycle_state=ended, ended_at or final_snapshot_confirmed for process shutdown. Persist through the normal document storage seam; `collaboration/lifecycle.ts` user-ending logic remains distinct. Close transiently with WebSocket 1012/service-restart behavior, not `session-ended` or `access-removed`; browser obtains fresh tickets and retains unconfirmed local text using existing reconnect behavior. Server acceptance means an authorized update actually applied before final freeze completion, not merely receipt/broadcast or a newly invented client ack.

### 4. Worker, digest, extraction and semantic settlement

Stop-claim signal ends polling/scheduling/backfill entry; distinct force-cancel signal is reserved for deadline/fatal cleanup. Register runOnce/schedule/backfill work before claim or BEGIN. An in-flight claim is owned even when its result arrives after cutoff: settle the acquired attempt with existing ownership fences, without starting another claim. Unclaimed pending jobs may remain.

Active work keeps existing heartbeat and extraction child processes until operation and fenced queue/outbox outcome commit. Include every outstanding heartbeat query at teardown; stop interval and await in-flight queries without renewing a committed/released attempt. Verify row counts/current owner/attempt/lease where required, including general jobs and digest outcomes; a zero-row or uncertain outcome fails drain rather than silently returning processed=true. Do not reset leases, decrement attempts or requeue solely to make shutdown look clean. Existing defined durable retry/cancel paths remain valid only when confirmed and no effect is uncertain.

All general/extraction/searchable-PDF lanes, scheduling reconciliation, digest composition/math worker, S3 image fetches/deletes/publication, semantic backfill and temporary-directory cleanup belong to their owner. Await children/worker threads and heartbeat completion, not only clear timers. Ambiguous provider acceptance or accepted send followed by failed/unknown commit blocks replacement even if a retry intent exists; no new exactly-once guarantee. Use fake sender tests only. Expected permanent/retry business outcomes may settle if committed and effect is known.

At deadline synchronously latch timeout/FAILED, stop claims, cancel active work, abort storage requests where supported, terminate remaining children/sockets, and perform bounded best-effort closure. All phases including evidence publication share the original 120s budget; reserve a small finalization slice within it, never add a fresh timeout per resource. If graceful work uses the budget, timeout is inevitable. Hard-exit fallback prevents a hung pool/filesystem/child from retaining the process beyond the deadline; best-effort timeout receipt may be absent. Missing evidence blocks replacement. Forced cleanup cannot turn timeout into success. Fatal failure cleanup uses the same ownership ordering where safe and never yields exit 0.

### 5. Ordered closure and truthful exits

Sequence: cutoff -> settle startup/admissions/active owners -> confirm frozen documents and fenced outcomes -> close role transports/listeners/callbacks -> close shared S3 clients, database pools and observability after all users -> publish durable terminal receipt -> exit. Actual adapters may overlap independent owner drains, not reorder dependencies. Check all closure errors. Exit 0 only after no unresolved work/uncertainty, complete required closure and successful receipt publication. Exit 1 for other failure/evidence failure; exit 2 when deadline expires (timeout takes precedence over other failures). No finally-exit(0). STOPPED is reached only following success publication; failures remain FAILED even if cleanup later finishes.

### 6. Durable evidence and approved operation binding

Environment is immutable in running processes; `docker exec` cannot change PID 1's environment. A startup-only operation ID would require an unnecessary writer restart and cannot bind a newly requested replacement. Approved operation binding: a private host-staged request file in an already mounted directory, staged before SIGTERM and read once after admission cutoff. SIGTERM remains the only trigger; this is not a control endpoint or watcher. The user explicitly approved this file contract, including exact boot/release/image/nonce validation, in the planning follow-up; no redundant approval is required.

Approved mount separation (host paths and integration assignment remain provisional until security coordination): separate `/run/chalktalk-lifecycle/requests` read-only and `/var/lib/chalktalk-lifecycle/evidence` writable. Host storage survives container removal and is separate from Supabase/DB/S3 and log spool. Each boot generates a random UUID; atomically publishes an identity descriptor with role/boot/release/image and timestamp before becoming RUNNING. Host inventories that descriptor against inspected container ID/start/restart count/immutable image digest, never trusts mutable `:local` tags or a descriptor alone. One process per container; missing/duplicate identity fails replacement inventory.

Host stages `requests/<boot-id>.json` atomically before SIGTERM containing schemaVersion, operationId, role, bootId, immutable release/image identity and a random single-use request nonce. IDs are bounded opaque identifiers (UUID for operation/boot/nonce); no free-form user data. The app validates regular-file/no-symlink path, bounded bytes, strict fields and exact own identity. Missing request means ordinary shutdown with operationId=null; malformed/mismatched/unreadable present request is evidence failure. If a request arrives after the single read, ordinary shutdown cannot satisfy replacement; do not infer/bind operation after exit. Verifier stores the inventoried tuple and nonce before signaling, rejects reuse by another operation, and requires this same tuple in receipt. No boot restart merely to label an operation. No hot polling, database control table or new dependency.

Receipts use schemaVersion, role, bootId, immutable releaseId/imageDigest, nullable operationId/requestNonce, signal/trigger, bootStartedAt, cutoffAt, completedAt, deadlineMs, elapsedMs, result (success/failure/timeout), exitCode and fixed-key counts (activeAdmissions/handlers/stores/jobs/heartbeats/children/listeners/unresolved) plus bounded allowlisted failure codes. No document/course/user IDs, SQL, object keys, email, tokens, paths, exception messages or payloads. Non-business instance/release/operation IDs belong only in local evidence, never public probes.

Use built-in fs: exclusive temporary file in same directory, restrictive permissions, full write, file fsync, atomic rename to immutable boot-specific terminal name, directory fsync. Descriptor publication uses the same discipline. Refuse overwriting another boot/receipt; no shared latest.json as proof. Any write/fsync/rename/directory-sync failure prohibits success. Test actual Linux host-bind filesystem support; unsupported durability is a blocker, not a silent fallback. If success was renamed before directory fsync fails, exit nonzero invalidates it; never accept receipt alone. No receipt can prove its own future exit.

Replacement consumer (Supabase owner, not implementation here) must require exact operation/nonce + every inventoried role/boot/container/release/image, success result, zero remaining counts, elapsed within deadline and observed exit 0 after cutoff; collect before remove. Reject missing/extra/unexpected writer instances, stale/duplicate/cross-operation proofs, nonzero/signal termination, OOM/KILL, restart or changed boot/start/image, no observed exit, partial/malformed evidence. Reinventory and hold old writers stopped/fenced through capture/cutover; a new boot invalidates the evidence set. Zero exit with no receipt is insufficient; success receipt with OOM/nonzero exit is insufficient. External scripts/dashboard/other deployment/DB/S3 writer inventory and credential fencing remain explicit operator work.
