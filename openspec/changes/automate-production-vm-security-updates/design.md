## Decisions

### 1. One authoritative security policy, not additive defaults

Create a late, root-owned APT configuration fragment that clears both `Unattended-Upgrade::Allowed-Origins` and `Unattended-Upgrade::Origins-Pattern` before setting exact origin/archive matches. Allow `Ubuntu:<codename>-security`, `UbuntuESMApps:<codename>-apps-security` and `UbuntuESM:<codename>-infra-security` only where configured, authenticated and available. Do not attach Ubuntu Pro, obtain credentials, add repositories or enable entitlements. An unavailable ESM source does not block ordinary security maintenance, but its availability is reported. No bare release pocket, `-updates`, proposed, backports, Docker or arbitrary origin is eligible. If a security fix requires a forbidden dependency, keep it back and report it rather than widening policy.

Preserve existing operator/distro package exclusions and append idempotent managed anchored package-family expressions for Docker (`docker`, `docker.io`, `docker-ce`, `docker-ce-cli`, `docker-ce-rootless-extras`, buildx and Compose plugins, including applicable suffixed variants), containerd (`containerd`, `containerd.io`) and `runc`. Do not apt-mark hold or remove installed packages: normal bootstrap's explicit install behavior stays separate. Verify actual package-name matching, not substring expectations. Preserve conffiles noninteractively, do not enable automatic removals, and explicitly set `Automatic-Reboot` and `Automatic-Reboot-WithUsers` false and unattended mail off. Set periodic metadata and unattended execution to `always` on timer invocation so a 23.5-hour interval cannot skip the next day's randomized run; disable redundant APT random sleep and set update error mode to reject partial metadata-refresh failure. Validate these options on each packaged Ubuntu version.

Read merged configuration using `apt-config dump` and unattended-upgrade's actual engine. Bootstrap must detect conflicting later configuration and fail before enabling the timers; each automatic run checks effective policy and refuses to install if it is widened or reboot enabled. Do not delete operator fragments to hide a conflict. Use exact distro Release metadata, not hostname substring matching. A signed third-party source can assert misleading metadata, so trusted repository/key administration remains an operator responsibility.

Alternative rejected: editing only `50unattended-upgrades` or appending an allowlist, since inherited lists and later overrides can widen eligibility. Do not replace the distro resolver with a custom package manager.

### 2. Preserve distro APT timers and catch-up

Use drop-ins for `apt-daily.timer` and `apt-daily-upgrade.timer`, resetting the inherited `OnCalendar` list. Metadata runs at `03:00 UTC` with 0–30 minutes delay; install runs at `04:00 UTC` with 0–30 minutes delay. Set `Persistent=true`, `RandomizedDelaySec=30m` and `AccuracySec=1us` on both. This is a start schedule, not a deadline for completion. Retain network ordering and the upgrade service's dependency on metadata; ensure catch-up also refreshes stale metadata before installation. Set service-level APT random sleep to zero so no second multi-hour jitter defeats the schedule.

Retain distro service functionality and only wrap its existing `apt.systemd.daily update|install` command to coordinate locks/holds and record trustworthy results. Do not add a cron runner or second timer. Reload systemd and enable/restart timers only after verification; never restart/stop an active package service as part of reconciliation. Catch-up can run outside the nominal window after downtime; this is intentional. Do not use wall-clock window restrictions that defeat persistence.

### 3. Normal service restarts, narrowly deferred runtime restarts

Manage a needrestart drop-in that allows normal automatic host service restarts but sets the service selection override to false for exact Docker and containerd units (including actual names/aliases observed on all supported releases). Use `override_rc`, not a blacklist that hides the processes from detection. Verify the installed release's effective needrestart behavior and invocation flags, since an APT hook can override config defaults. Do not disable needrestart globally, edit Docker daemon configuration, change live-restore, restart runtime units, or claim continuous application availability. Package maintainer scripts and ordinary service restarts can still disrupt connections; excluded runtime packages reduce rather than eliminate risk.

### 4. Bounded waits and persistent holds at the existing host lock

Keep `/srv/chalktalk/shared/deploy.lock` as the shared host rendezvous; do not introduce a second competing lock domain. Ensure its directories/file exist safely before first bootstrap APT mutation and preserve existing ownership and secret-directory permissions. Automatic metadata/install wrappers take this flock with a 600-second wait and keep it through the entire child command, including package hooks. The wrapper remains alive holding its descriptor until the child exits; a child closing inherited descriptors must not release the parent's lock. Do not add service start/runtime timeouts that terminate a live package transaction. Deployment stage/finish also use a 600-second wait. Native APT/dpkg locks remain authoritative against unrelated package commands; set `lock_timeout: 300` on every bootstrap APT task, including prerequisites, Docker and maintenance-package installation. Timeout reports failure and exits without deleting lock files, killing dpkg/APT, or resetting package state. The limit covers waiting, not transaction runtime; never wrap a live package transaction in a hard timeout that kills it.

Use root-owned `/var/lib/chalktalk-maintenance/` (0755) for persistent, sanitized hold/state files (0644); non-root users can read but cannot create/remove holds. Root-issued hold set/clear operations acquire the same flock with the same bounded wait and atomically create/remove a marker. Thus a hold is acknowledged only after any already-running transaction releases the lock; if waiting expires, report not acquired, never interrupt it. Automatic wrappers acquire the flock, then inspect holds immediately before spawning APT; checking only before waiting is racy.

Use distinct `update.hold` and `deployment.hold` files. The update hold suppresses both automatic metadata refresh and security installation, not deployment. The deployment hold refuses new `stage` work before filesystem/release/Compose mutation, including a recheck after waiting; it does not suppress maintenance or prevent an already-staged SHA's `finish` bookkeeping. Placing a deployment hold waits for any active stage to release the lock. Existing stage/finish split and external HTTPS checks stay intact; no attempt to maintain a long-lived distributed lease between SSH sessions. APT transactions may occur between stage and finish, which is acceptable given the approved restart risk.

Bootstrap creates a separate root-owned `bootstrap.hold` under the same flock before package work, waiting for active automatic maintenance without stopping it. All wrappers respect it. Clear only the current bootstrap invocation's token-owned marker after successful verification; leave it on failure for explicit operator inspection/clear. Never clear an existing operator update hold or another bootstrap marker. A rerun encountering a leftover bootstrap marker fails with recovery guidance rather than taking it over silently. On the first rollout, stock APT services may already be running outside the new wrapper: wait boundedly for their native locks, do not stop them, and install drop-ins without restarting active services. Existing manual package operations are not claimed to share deployment flock.

Alternative rejected: deleting locks, stopping active services, killing dpkg, blanket masking timers, or using the update hold as a deployment freeze. Holds are persistent safety controls, not an implicit expiry or an instruction to roll back installed packages.

### 5. Read-only maintenance signal, no new delivery service

The production-contact job is disabled by default, including manual dispatch. Its job-level condition requires `vars.PRODUCTION_VM_MAINTENANCE_CHECK_ENABLED == 'true'` and trusted main execution. Use a repository-level variable so the job can be skipped before production environment approval or secret resolution. Missing, false and any non-exact value must cause no SSH/tool installation/host validation or other VM contact. The workflow may exist on main without activating production checks. Only a separately authorized operator may set the variable; implementation never changes GitHub settings. Tests execute the gate's semantic cases and mock SSH to prove missing/default-false skips all connection attempts. The feature operations note documents explicit opt-in and disabling by removing/setting false, plus notification prerequisites. This approval changes the earlier scheduled-check rollout: default-branch presence alone is not activation.

Add `.github/workflows/vm-maintenance-check.yml`: daily `06:17 UTC` schedule plus manual main-only dispatch, `contents: read`, production environment, the same `chalktalk-production-vm` group and `cancel-in-progress: false`. Use existing SHA-pinned checkout action and the existing port-22 pinned-host-key SSH pattern. Only SSH identity/address/known-host secrets are needed; no database, application, Resend or Storage secrets. Validate host and pinned entry before connection; bounded SSH connect/read/check runtime failures fail the job. Never bootstrap/install tools, refresh APT, clear holds, restart services, change settings or mutate state from this check.

A root-owned local status helper uses read-only/in-memory APT cache access and never opens a package transaction or updates package lists. It reads merged policy, systemd service results/timer state, successful-operation evidence, current cached security eligibility, `dpkg --audit`, reboot-required, needrestart batch list-only output, holds, and filesystem blocks/inodes. It emits versioned sanitized JSON plus a concise human summary, using no production env files or unrestricted journal dumps. Call through existing noninteractive sudo only to read privileged state. Use no new sudoers policy and never eval host output in Actions.

Recommended explicit operational thresholds for this plan: metadata or completed security evaluation older than 48 hours is stale; missing, corrupt or future-dated timestamps are unknown/failing. The first installation remains unknown until real maintenance succeeds, not healthy at bootstrap. Low disk is less than 2 GiB OR less than 10% available blocks on `/`, `/var`, or `/srv/chalktalk` (deduplicate backing filesystems), or less than 10% free inodes. Check reports units/thresholds in its output. Healthy/no-security-updates is distinct from skipped, running, held, failed, unsupported and unknown. An active run can be reported running with age; it must not erase a previous failure/stale condition.

Store last attempt, disposition and last verified successful metadata/security evaluation separately in atomic root-owned state, without resetting success age on holds, lock timeouts, errors, bootstrap or skipped work. Do not trust systemd exit zero alone: distro `apt.systemd.daily` can hide child errors/no-ops. Cross-check real APT success stamps and unattended result evidence from the installed version; fail closed if evidence cannot prove completion. Successful evaluation with no candidates counts, but deferred/failed packages are reported separately. Policy drift, disabled timers, nonempty dpkg audit, pending eligible security updates after an attempted run, or unavailable evidence fail the check. Detect deferred Docker/containerd restarts from needrestart's actual list-only result; configuration exclusions alone are not proof a restart is needed. Unsupported/failed detection is unknown, not false.

For actionable failures, stale/unknown state, any hold, pending reboot, deferred runtime restart or low disk, emit all reasons in the job summary and exit nonzero so GitHub can notify. Report package identifiers and timing only; no secrets/full command environments. GHA scheduling and concurrency can delay checks or replace pending jobs; this is not a guaranteed-time external watchdog. Operators must enable GitHub Actions failure notifications and verify delivery with an intentionally failing read-only test; code cannot turn on personal notification settings or prove email receipt. No Resend, SMTP agent or external service is added.

## Verification strategy

Use existing unittest/Ansible tooling and Docker; no Molecule, VM orchestration dependency, new framework or third-party test service. In vertical slices, write a spec-derived observable test, demonstrate the expected red failure, implement the minimum, then prove green. Source/YAML assertions are supplementary only.

The acceptance entry point will be `bash deployment/production/ansible/tests/maintenance-acceptance.sh 22.04|24.04|26.04`. It creates only disposable Docker guests with real systemd as PID 1 (not chroot/fake systemctl), distro Python/APT/needrestart/unattended-upgrades installed, no production inventory/secrets and no host filesystem mounts. Privileged/cgroup setup is isolated to ephemeral CI runners; never run this harness on the production host. Record distro, package versions and distro image digests. Reuse existing Docker and pinned controller tools; install only distro guest prerequisites. If real systemd cannot run, fail acceptance rather than substitute mocks or skip a release.

Use a temporary, guest-only signed APT fixture repository with independently declared Release origin/archive metadata and package versions. Include security, available ESM security, bare release, updates/proposed/backports, third-party, Docker and containerd candidates plus a security package with a forbidden dependency. Trust the fixture key only inside the guest; never copy a real ESM token. Run real `apt-get update`, `apt-config dump`, `apt-cache policy`, `unattended-upgrade --dry-run --debug`; assert candidates and blocked packages, and exercise a harmless fixture transaction to prove permitted install/exclusions without production packages. Include an ESM-unavailable case and explain synthetic ESM validates selection, not a live entitlement.

Check `systemctl cat/show`, `systemd-analyze calendar`, service executions and timer downtime/reactivation with a deterministic short-lived test-only schedule. Assert effective UTC calendars, clearing inherited events, jitter/accuracy, metadata-before-install and Persistent catch-up; time-compressed tests never alter production templates. Compare all managed file hashes and ownership/modes after two Ansible runs: second configuration application has no changes; runtime status/timer timestamps are excluded from hash equality, and existing holds are preserved. Test conflicting late APT config and no-reboot enforcement using real merged policy.

Exercise real flock contention in guest subprocesses (not only the existing flock mock): bounded acquisition, hold-after-wait race, active transaction completion despite hold request, lock timeout with no mutation, separate deployment/update holds, bootstrap fail-retained marker and token ownership. Verify reboot/live-restore unchanged, runtime restart exclusions via actual effective needrestart policy, ordinary eligible fixture service restart and a controlled obsolete-process scenario producing deferred runtime detection. Avoid restarting a real Docker daemon in the guest. Fake only external deployment/SSH interfaces for local tests, not APT selection/systemd semantics.

Fixture-clock status tests cover threshold boundaries, stale/missing/future/corrupt evidence, partial APT failures masked by outer success, running/held/no-candidates, reboot-required, deferred runtime units, blocks/inodes, absent detectors, malformed JSON and multiple simultaneous reasons. Snapshot hashes before/after the production-mode status command to prove read-only behavior. Workflow tests verify trusted main, minimal secrets, pinned host identity, shared non-canceling concurrency, summary rendering and failure exits. No frontend files change, so browser tests/screenshots are not applicable.

## Risks / Trade-offs

- Single-host restarts and security-only dependency deferral → acknowledge downtime risk, report deferred work; no automatic widening or reboot.
- Stock APT behavior differs by release and may mask errors → real three-release policy/transaction/systemd acceptance plus fail-closed success evidence.
- Hold left after bootstrap failure can halt patching → persistent visible state and failing status report, explicit operator recovery; never silently clear it.
- Ubuntu packages may later override effective config → validate after bootstrap and before each automatic install; report drift.
- GHA is neither guaranteed timely nor an independent availability service → document delay/notification limitations and operator verification.
- Runtime package/restart exclusion leaves manual security work → report known pending restarts and excluded runtime upgrades, require separately authorized maintenance.
